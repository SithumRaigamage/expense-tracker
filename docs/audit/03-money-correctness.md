# 🟡 Medium — Money Correctness

Wallet balances are stored as a running total that each endpoint must keep in step
with the transaction history. The defects below let the two drift apart.

| ID | Issue | Location | Verification | Status |
|---|---|---|---|---|
| M1 | Changing an expense's category between an **expense** type and an **income** type doesn't rebalance the wallet. Balances are only adjusted when `amount` or `wallet` change, so moving 100 from *Food* to *Salary* should shift the balance by +200 but shifts it by 0. | `services/expenseService.js` (`updateExpense`) | Reproduced | ✅ Fixed: `updateExpense` compares the entry's whole balance effect (amount signed by category type) before and after, so a type flip, an amount change and a wallet change are handled by one rule. A non-numeric or zero amount is rejected before any balance moves (it used to `$inc` by `NaN`). Regression: `tests/integration/expense.test.js`. |
| M2 | Deleting a category leaves its expenses without one. `deleteExpense`/`updateExpense` then read `expense.category.type` on `null` and fail with **500**, and the frontend mapper (`expense.category.name`) throws, which can empty the transaction list. | `services/categoryService.js` (`deleteCategory`), `services/expenseService.js:250`, frontend `services/transaction.service.ts` | Reproduced | ✅ Fixed: a category in use can't be deleted on its own (409); `DELETE /categories/:id?reassignTo=<id>` moves its transactions to another category of the **same type** (so no balance changes) and deletes it, in one transaction. Entries orphaned earlier no longer cause a 500: update/delete answer 409 until they're given a category (a label repair; their original type is unknown). The frontend maps them as "Uncategorized" instead of throwing. Regression: `tests/integration/categoryDelete.test.js`, `transaction.service.spec.ts`. |
| M3 | Deleting a wallet (soft delete) makes its expenses impossible to edit or delete: `updateBalance` requires an active wallet and answers *"Wallet not found"*. | `services/walletService.js` (`deleteWallet`, `updateBalance`) | Reproduced | ✅ Fixed: `updateBalance` takes `includeInactive`, used only for entries a wallet already holds. Editing, deleting or moving an entry out of a soft-deleted wallet works and keeps its (restorable) balance true; new expenses, transfers, payments and entries moved *into* it are still rejected. Regression: `tests/integration/expense.test.js` ("expenses in a deleted wallet"). |
| M4 | Transfers, goal contributions and bill payments ignore currency, so moving 100 from an LKR wallet into a USD wallet moves "100". The chat's *"Total across all wallets"* also sums different currencies together. | `walletService.transferFunds`, `productBudgetService.contribute`, `billService.payBill`, `chatService.buildFinancialContext` | Code review | ⏳ Open |
| M5 | The shipped compose file runs MongoDB as a single standalone server, which can't run transactions, so every multi-write money operation silently falls back to separate writes. Those also read the balance, modify it in memory and `save()` it back, so two concurrent requests overwrite each other. Prefer atomic `$inc` with a guard (`balance: { $gte: amount }`), and/or run MongoDB as a single-node replica set. | `walletService.transferFunds`, `productBudgetService.contribute`, `billService.payBill`, `docker-compose.yml` | Code review | ✅ Fixed: balances change only via one atomic `$inc`, with the sufficient-funds (and goal-target) guard in the same filter; every multi-write money operation runs in a transaction (`utils/transaction.js`); both compose files and `ensure-mongo.sh` run a single-node replica set. Also fixed: concurrent first-ever transfers/bill payments failed creating their system category (now an upsert). Regression: `tests/integration/moneyConcurrency.test.js`. |
| M6 | Funding a savings goal debits the wallet but records no transaction, so the money disappears from history and analytics. Bill payments, by contrast, record an expense. | `services/productBudgetService.js` (`contribute`) | Code review | ⏳ Open |
| M7 | Bills: a subscription can be paid twice by double-submitting (only one-off bills set `paidAt`). Month roll-over uses `setMonth(+1)`, so a Jan 31 due date becomes Mar 3. Recurring expenses have the same overflow. | `services/billService.js:143`, `utils/recurrence.js:25` | Code review | ⏳ Open |
| M8 | `getExpenseStats` and `getMonthlyStats` add income and expense transactions together into one "total" without checking the category type. | `services/expenseService.js` | Code review | ⏳ Open |
